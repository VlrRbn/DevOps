# Урок 83. Масштабирование Lambda с SQS: concurrency и backpressure

## 1. Зачем нужен этот урок

В уроке 82 мы разобрали контракт корректной пакетной обработки SQS:

```text
получить пакет
-> независимо обработать записи
-> вернуть точные messageId неудачных записей
-> повторить только неудачные записи
```

Корректная обработка ошибок необходима, но она не отвечает на вопрос о мощности системы:

> Что произойдёт, если сообщения поступают быстрее, чем функция успевает их обрабатывать?

Без явного ограничения сопоставление источника событий (event source mapping) для SQS может быстро масштабировать Lambda. Очередь опустеет быстрее, но функция может перегрузить базу данных,
исчерпать квоту внешнего API или региональную квоту Lambda и неожиданно увеличить стоимость.

В этом уроке создадим контролируемую разницу скоростей:

```text
20 сообщений приходят одним всплеском
-> обработка одного сообщения занимает около 8 секунд
-> event source mapping разрешает 2 одновременных вызова
-> часть сообщений остаётся видимой в SQS
-> два сообщения обычно находятся в обработке
-> накопившаяся очередь постепенно опустошается
```

Накопление сообщений не всегда означает отказ. Очередь принимает нагрузку, которую
ограниченный потребитель не может обработать сразу. Задача эксплуатации: понять,
остаётся ли возраст сообщений допустимым.

## 2. Результаты урока

После урока ты сможешь:

- различать одновременное выполнение (concurrency), пропускную способность, накопившуюся
очередь (backlog) и сдерживание нагрузки (backpressure);
- приблизительно вычислить скорость обработки Lambda с SQS;
- ограничить одно сопоставление источника SQS через `MaximumConcurrency`;
- отличить лимит источника от зарезервированной мощности функции;
- объяснить разницу между `reserved concurrency` и `provisioned concurrency`;
- создать воспроизводимый всплеск сообщений без внешней зависимости;
- наблюдать глубину очереди, не конкурируя с механизмом опроса Lambda;
- сопоставить глубину SQS, возраст старейшего сообщения, число одновременных вызовов Lambda

- объяснить, когда накопление сообщений является полезной буферизацией, а когда сигналом инцидента;
- безопасно удалить временную лабораторию.

## 3. Ментальная модель

### 3.1. Одновременное выполнение не равно пропускной способности

Одновременное выполнение показывает текущее состояние:

```text
Сколько вызовов Lambda выполняется прямо сейчас?
```

Пропускная способность показывает скорость:

```text
Сколько сообщений завершается за секунду или минуту?
```

Два одновременных вызова не означают два сообщения в секунду. Если один вызов
обрабатывает одно сообщение восемь секунд, приблизительная скорость равна:

```text
service_rate ~= concurrency * batch_size / average_duration
service_rate ~= 2 * 1 / 8
service_rate ~= 0.25 сообщения/секунду
```

Для двадцати сообщений получаем:

```text
drain_time ~= message_count / service_rate
drain_time ~= 20 / 0.25
drain_time ~= 80 секунд

Или:

20 сообщений / 2 одновременно = 10 волн
10 волн * 8 секунд = ~80 секунд
```

Это оценка, а не SLO. Холодные запуски, опрос, запись журналов, частичные ошибки,
повторы и разная продолжительность изменят фактический результат.

### 3.2. Накопившаяся очередь хранит необработанную нагрузку

Предположим:

```text
arrival_rate > service_rate

arrival_rate = 5 msg/s
service_rate = 3 msg/s
backlog growth ≈ 2 msg/s
```

Тогда очередь растёт:

```text
всплеск от отправителя
-> SQS принимает сообщения
-> ограниченный потребитель обрабатывает по два сообщения одновременно
-> остальные сообщения накапливаются в очереди
```

Важнее не только **сколько**, но и **как долго они ждут**.

SQS разделяет приём и завершение обработки. Отправители могут успешно передавать
сообщения, пока потребитель отстаёт. Это полезная буферизация, но теперь нужно ответить:

```text
Насколько старым может стать сообщение, прежде чем бизнес-результат потеряет смысл?
```

Для глубины очереди нет универсального порога. Десять сообщений могут быть критичны
для авторизации платежа и несущественны для ночного отчёта. Допустимый возраст должен
быть связан с бизнес-целью по задержке.

### 3.3. Три разных ограничения одновременного выполнения

| Ограничение | Область действия | Резервирует мощность? | Значение в лаборатории |
|---|---|---:|---:|
| `MaximumConcurrency` источника | Одно сопоставление источника SQS | Нет | `2` |
| `reserved concurrency` функции | Все источники одной функции | Да | `null` |
| Квота одновременных вызовов аккаунта | Все функции одного региона | Региональная квота | Значение аккаунта |

Фактическое число одновременных вызовов ограничено всеми применимыми границами:

```text
фактическая concurrency
= минимум(
    лимита сопоставления SQS,
    reserved concurrency функции, если задана,
    доступной concurrency аккаунта,
    текущего спроса и поведения масштабирования Lambda
  )
```

Лимит источника защищает нижестоящую систему. Он не резервирует мощность, поэтому
другая функция всё ещё может занять общий региональный пул.

Зарезервированная мощность функции действует сразу в двух направлениях:

```text
резервирует мощность для функции
+
ограничивает функцию тем же числом
```

Пример конфликта:

```text
лимит сопоставления = 5
reserved concurrency = 2
  - сопоставление потенциально требует больше,
      чем функция может запустить
  - возможны Throttles
```

Не устанавливай зарезервированную мощность функции ниже суммы лимитов всех её сопоставлений SQS.
Иначе Lambda может ограничивать уже принятые из очереди задания.

### 3.4. Зарезервированная мощность не означает заранее подготовленную

Эти названия легко перепутать:

| Возможность | Основная задача | Прогревает среды? | Дополнительная плата? |
|---|---|---:|---:|
| Reserved concurrency | Изоляция мощности и верхняя граница | Нет | Нет |
| Provisioned concurrency | Предсказуемая задержка запуска | Да | Да |
| SQS provisioned mode | Выделенные механизмы опроса и ускоренное масштабирование источника | Не среды функции | Да |

То есть `reserved concurrency` про изоляцию вычислительной ёмкости, `provisioned concurrency`
про готовность к быстрому старту.

Лаборатория не использует платные возможности с заранее выделенной мощностью.
Зарезервированная мощность также выключена: у учебного аккаунта может быть небольшая квота,
а Lambda должна сохранить минимальный общий незарезервированный пул.

### 3.5. Maximum Concurrency относится к одному источнику

Terraform-ресурс содержит:

```hcl
scaling_config {
  maximum_concurrency = var.event_source_maximum_concurrency
}
```

Для SQS AWS принимает значения от `2` до `1000`. В лаборатории используется
минимум, чтобы постепенное опустошение очереди было хорошо заметно.

Если две очереди подключены к одной функции, у каждого сопоставления может быть свой лимит:

```text
сопоставление срочной очереди -> максимум 8
сопоставление фоновой очереди -> максимум 2
одна функция Lambda           -> суммарный спрос до 10
```

Если у функции настроена зарезервированная мощность, она должна быть не меньше суммы
лимитов этих источников.

### 3.6. Ограничение вызовов не является нормальным управлением нагрузкой

Лимит источника не позволяет запросить больше настроенных одновременных вызовов.
Это намеренное управление потоком.

Нормальное ограничение:

```text
SQS
↓
сопоставление разрешает максимум 2
↓
Lambda запускается нормально
↓
остальные сообщения ждут в очереди
```

Throttling:

```text
сопоставление пытается запустить Lambda
↓
доступной concurrency нет
↓
запуск отклоняется
↓
сообщение остаётся неподтверждённым
```

Ограничение вызова означает, что он не смог начаться из-за другой границы мощности:

```text
сопоставление запрашивает вызов
-> у функции или аккаунта нет доступной concurrency
-> Lambda отклоняет запуск
-> сообщение SQS остаётся неподтверждённым
-> действуют visibility timeout и правила повторов
```

Что происходит при throttling:

```text
MaximumConcurrency = 5
reserved concurrency = 2
```

Сопоставление потенциально хочет использовать до пяти одновременных вызовов, но
функция уже упёрлась в предел `2`.

Тогда:

```text
попытка вызова
↓
Lambda не может его начать
↓
Throttles растёт
↓
сообщение не подтверждено
↓
visibility timeout / retry
```

Нормальный поток нужно ограничивать на уровне источника, а не через отказы запуска.
Следи за метрикой `Throttles`: нулевое значение отличает ожидаемое накопление от конфликта мощностей.

```text
backlog + Throttles = 0
  - штатное ограничение потребления

backlog + Throttles > 0
  - уже проблема с доступной мощностью
```

### 3.7. Приблизительные метрики нужно сопоставлять

Атрибуты очереди SQS являются приблизительными:

| Сигнал | Как его понимаем | Ограничение |
|---|---|---|
| Видимые сообщения | Задания, доступные потребителям | Значение может обновляться с задержкой |
| Невидимые сообщения | Полученные и временно скрытые задания | Это не точная метрика одновременных вызовов Lambda |
| Возраст старейшего сообщения | Давление на задержку обработки | Задержка публикации и дискретность CloudWatch |
| Одновременные вызовы Lambda | Выполняющиеся вызовы | Обычно относится ко всей функции |
| Lambda throttles | Запуски, отклонённые из-за мощности | Не показывает, какой лимит стал причиной |

В лаборатории у функции только один источник, поэтому число одновременных вызовов можно использовать
как приближение для сопоставления.

Диагностическая таблица:

```text
visible      — backlog
in_flight    — сообщения уже получены
queue age    — задержка
concurrency  — выполняющиеся вызовы Lambda
throttles    — отклонённые запуски
logs         — фактическое перекрытие выполнения
```

## 4. Архитектура лаборатории

```text
send-burst.sh
     |
     | 20 заданий, work_seconds = 8
     v
+------------------------+
| стандартная очередь SQS|
| visibility = 95s       |
+-----------+------------+
            |
            | event source mapping
            | BatchSize = 1
            | MaximumConcurrency = 2
            v
+------------------------+
| ограниченный обработчик|
| Lambda timeout = 15s   |
| reserved = не задана   |
+-----------+------------+
            |
            +----> структурированные журналы CloudWatch

повторяющиеся ошибки
     |
     v
+------------------------+

+------------------------+
```

Успешный всплеск не должен задействовать DLQ. Она остаётся в архитектуре, потому
что масштабирование не заменяет ограниченные повторы и изоляцию ошибок из урока 82.

### 5.1. Контракт ограниченного задания

Открой:

```text
lab_83/app/lambda_function.py
```

Тело каждого сообщения:

```json
{

  "work_seconds": 8
}
```

Парсер принимает только число от нуля до десяти. Логические значения Python отклоняются
отдельно, потому что `bool` является подклассом `int`.

Задержка нужна только для измеримого учебного эксперимента. Если бы функция
выполнялась, например, за 50 мс, то 20 сообщений могли бы исчезнуть слишком быстро.

### 5.2. Зачем здесь `TypedDict`, `object` и `cast()`

Событие Lambda приходит извне, поэтому до проверки кода нельзя обещать, что это
словарь нужной структуры. По этой причине `lambda_handler()` принимает `event: object`:

```python
def lambda_handler(event: object, context: object) -> BatchResponse:
```

`object` означает: «значение существует, но его точный тип пока неизвестен».
`require_string_keyed_dict()` выполняет проверку во время работы программы и только
после неё возвращает `dict[str, object]`:

```python
def require_string_keyed_dict(
    value: object,
    error_message: str,
) -> dict[str, object]:
    if not isinstance(value, dict) or not all(
        isinstance(key, str) for key in value
    ):
        raise MessageContractError(error_message)

    return cast(dict[str, object], value)
```

Здесь работают два разных уровня защиты:

1. `isinstance()` и проверка ключей реально выполняются Python и отклоняют неверный ввод.
2. `cast()` выполняется только для анализатора типов. Он не преобразует значение в словарь и
   не заменяет проверку во время выполнения.

После разбора JSON мы уже знаем точную структуру задания. Её описывает `TypedDict`:

```python
class WorkItem(TypedDict):
    task_id: str
    work_seconds: float
```

Это не новый класс объекта и не замена словарю. Во время выполнения `item` остаётся обычным `dict`:

```python
item: WorkItem = {
    "task_id": "burst-task-1",
    "work_seconds": 8.0,
}
```

Разница видна в редакторе: Pylance теперь знает, что `item["task_id"]` содержит строку,
`item["work_seconds"]` — число, а неизвестный ключ является ошибкой.
Аналогично `WorkResult`, `BatchItemFailure` и `BatchResponse` фиксируют внутренний
результат и точный контракт частичного ответа для Lambda.

Итоговая последовательность выглядит так:

```text
непроверенный object
-> проверка словаря и ключей во время выполнения
-> проверка обязательных полей
-> TypedDict с известной структурой
-> безопасная обработка и подсказки Pylance
```

Не перепутать:

```text
object
  - "пока тип неизвестен"

isinstance()
  - реально проверяет данные

cast()
  - ничего не проверяет, только сообщает тип анализатору

TypedDict
  - описывает структуру обычного dict для анализатора типов
```

Аннотации не делают некорректный ввод безопасным сами по себе. Без проверок `isinstance()`
функция всё равно могла бы получить строку, `null` или словарь с неверными полями и
завершиться с `AttributeError`, `KeyError` или `TypeError`.

### 5.3. Структурированные журналы времени

Один успешный вызов записывает:

```text
batch_started
-> work_started
-> work_completed
-> batch_completed
```

```text
request_id -> какой именно вызов Lambda
message_id -> какое SQS-сообщение
task_id    -> какая бизнес-задача
elapsed_ms -> сколько реально заняла работа
```

Пример перекрытия:

```text
12:00:00 request-A work_started
12:00:01 request-B work_started
12:00:08 request-A work_completed
12:00:09 request-B work_completed
```

Так по журналам можно увидеть перекрывающиеся вызовы.

Поля `request_id`, `message_id`, `task_id` и `elapsed_ms` позволяют различать перекрывающиеся
вызовы. Глобальный счётчик Python не докажет общее число одновременных вызовов: разные среды
выполнения не разделяют память процесса.

### 5.4. Отправка всплеска

`send-burst.sh` использует `SendMessageBatch` и передаёт не более десяти записей
за один API-вызов. Скрипт:

```text
получить параметры
-> проверить их
-> разбить COUNT сообщений на пакеты максимум по 10
-> собрать JSON для SendMessageBatch
-> отправить все пакеты в SQS
-> сохранить ответы AWS
-> посчитать Successful / Failed
-> завершиться ошибкой, если хотя бы одна запись не отправилась
```

### 5.5. Безопасная выборка состояния очереди

Есть два способа посмотреть на очередь:

```text
посмотреть атрибуты очереди
  - просто наблюдаем состояние

ReceiveMessage
  - реально забираем сообщения
```

`sample-backlog.sh` вызывает только `GetQueueAttributes`. Он не выполняет `ReceiveMessage`,
поэтому не скрывает сообщения и не конкурирует с Lambda.

Что делает скрипт целиком:

```text
получить параметры
  - проверить интервал и число выборок
  - создать TSV-файл
  - несколько раз вызвать GetQueueAttributes
  - записать timestamp + visible + in_flight + delayed
  - между выборками ждать заданный интервал
```

Столбцы TSV:

```text
timestamp  visible  in_flight  delayed
```

Не считай `in_flight` точным счётчиком одновременных вызовов. Для доказательства используй
метрики Lambda и перекрывающиеся `request_id` в журналах.

## 10. Сопоставление журналов и метрик

Проверь структурированные журналы:

```bash
aws logs tail "/aws/lambda/${FUNCTION_NAME}" \
  --region "$AWS_REGION" \
  --since 15m \
  --format short | grep -E 'work_started|work_completed'
```

Разные перекрывающиеся `request_id` доказывают одновременные вызовы. Повтор одного
`task_id` означал бы повторную доставку: реальный побочный эффект нужно защищать границей
идемпотентности из урока 81.

После публикации данных CloudWatch запроси число одновременных вызовов Lambda:

```bash
export METRIC_END="$(date -u +%Y-%m-%dT%H:%M:%SZ)"
export METRIC_START="$(date -u -d '20 minutes ago' +%Y-%m-%dT%H:%M:%SZ)"

aws cloudwatch get-metric-statistics \
  --region "$AWS_REGION" \
  --namespace AWS/Lambda \
  --metric-name ConcurrentExecutions \
  --dimensions Name=FunctionName,Value="$FUNCTION_NAME" \
  --start-time "$METRIC_START" \
  --end-time "$METRIC_END" \
  --period 60 \
  --statistics Maximum \
  --query 'sort_by(Datapoints,&Timestamp)[].[Timestamp,Maximum]' \
  --output table
```

Для этой изолированной функции и одного источника максимум не должен превышать двух.
Если точек нет, публикация метрики могла ещё не завершиться. Подожди и повтори.

То есть теперь у нас два взаимодополняющих доказательства:

```text
Журналы
  - реально были перекрывающиеся вызовы
  - число одновременных вызовов достигало как минимум 2

CloudWatch ConcurrentExecutions
  - максимум функции = 2
  - выше лимита сопоставления функция не поднималась
```

Проверь ограничения мощности (Throttles):

```bash
aws cloudwatch get-metric-statistics \
  --region "$AWS_REGION" \
  --namespace AWS/Lambda \
  --metric-name Throttles \
  --dimensions Name=FunctionName,Value="$FUNCTION_NAME" \
  --start-time "$METRIC_START" \
  --end-time "$METRIC_END" \
  --period 60 \
  --statistics Sum \
  --query 'sort_by(Datapoints,&Timestamp)[].[Timestamp,Sum]' \
  --output table
```

Нормальный результат: `0` или отсутствие точек `Throttles`.

## 11. Отрицательные упражнения и оценка мощности

### Упражнение 1. Отклони недопустимый лимит источника

```bash
terraform plan \
  -var='event_source_maximum_concurrency=1'
```

Ментальная модель:

```text
пользователь задаёт 1
↓
проверка Terraform проверяет переменную
↓
значение нарушает контракт
↓
plan останавливается
↓
AWS вообще не вызывается
```

Ожидаемый результат:

```text
event_source_maximum_concurrency must be an integer between 2 and 1000.
```

Ошибка возникает до обращения к AWS API.

### Упражнение 2. Отклони зарезервированную мощность ниже лимита источника

```bash
terraform plan \
  -var='event_source_maximum_concurrency=3' \
  -var='function_reserved_concurrency=2'
```

То есть архитектурно получается конфликт:

```text
сопоставление источника событий: максимум 3
            ↓
Lambda function: максимум 2
            ↓
третий запуск потенциально некуда разместить
            ↓
возможен throttling
```

Ожидаемый результат:

```text
function_reserved_concurrency must be at least event_source_maximum_concurrency.
```

Предусловие предотвращает известный конфликт, приводящий к ограничению вызовов.

### Упражнение 3. Проверь равную зарезервированную мощность без применения

```bash
terraform plan \
  -var='event_source_maximum_concurrency=2' \
  -var='function_reserved_concurrency=2'
```

Структура плана корректна, но не применяй его. В уроке 78 мы уже видели, что аккаунт
с небольшой квотой может отклонить резервирование: Lambda должна сохранить минимальный
незарезервированный пул. Корректная связь Terraform не доказывает наличие квоты аккаунта.

### Упражнение 4. Оцени более быструю конфигурацию

Сначала вычисли, не применяя изменение:

```text
concurrency = 4
batch_size = 1
average_duration = 8 секунд

service_rate ~= 4 * 1 / 8 = 0.5 сообщения/секунду
время для 20 сообщений ~= 40 секунд
вместо прежних ~80 секунд
```

Затем проверь план:

```bash
terraform plan \
  -var='event_source_maximum_concurrency=4'
```

Перед таким изменением в боевой среде проверь мощность нижестоящей системы, квоту аккаунта,
стоимость, цель по возрасту очереди и процедуру отката.

## 12. Разбор типовых проблем

### Сообщения не накапливаются

Возможные причины:

1. `work_seconds` слишком мал.
2. Отправлено слишком мало сообщений.
3. `MaximumConcurrency` выше ожидаемого.
4. Выборка началась после опустошения очереди.

Проверь сопоставление источника и повтори сценарий с аргументами `20 8`.

### Очередь не опустошается

Проверь:

```bash
aws lambda get-event-source-mapping \
  --region "$AWS_REGION" \
  --uuid "$MAPPING_UUID" \
  --query '[State,StateTransitionReason,LastProcessingResult]' \
  --output table
```

```text
State
  - сопоставление находится в состоянии Enabled?

StateTransitionReason
  - почему он оказался в текущем состоянии?

LastProcessingResult
  - что происходило при последних попытках обработки?
```

Затем проверь журналы функции, `Errors`, `Throttles`, возраст исходной очереди и глубину DLQ.
Не выполняй `aws sqs receive-message` для исходной очереди во время диагностики:
команда изменит видимость сообщения и начнёт конкурировать с Lambda.

### Число сообщений в обработке не равно двум

Атрибуты SQS приблизительны, а у сопоставления источника есть внутреннее поведение
опроса. `ApproximateNumberOfMessagesNotVisible` не является точной метрикой
одновременных вызовов Lambda. Сопоставь его с `ConcurrentExecutions` и журналами.

### `PutFunctionConcurrency` отклонён

Если ты включил зарезервированную мощность, аккаунту может не хватить квоты после
сохранения обязательного незарезервированного пула. Верни переменную к `null`,
если резервирование не требуется и квота не была заранее проверена.

### Метрика Throttles не равна нулю

Проверь все границы:

```text
MaximumConcurrency сопоставления
reserved concurrency функции
другие источники этой же функции
доступную региональную concurrency
квоту concurrency аккаунта
```

```text
backlog + Throttles = 0 -> ожидаемое ограничение потребления

backlog + Throttles > 0 -> конфликт мощности / давление на квоту
```

### Метрики CloudWatch пусты

CloudWatch публикует данные с задержкой. Сначала подтверди выполнение по журналам,
подожди несколько минут и повтори запрос метрик с более широким интервалом.

### Последовательность диагностики

```text
очередь не опустошается
→ состояние сопоставления
→ журналы и ошибки
→ ограничения мощности
→ возраст очереди
→ DLQ
```

## 13. Стоимость и эксплуатационные границы

Лаборатория создаёт:

- одну функцию Lambda;
- одну стандартную исходную очередь и одну DLQ;
- одно сопоставление источника событий (event source mapping);
- одну IAM-роль и встроенную политику;
- одну группу журналов CloudWatch;
- три сигнала тревоги CloudWatch.

Упражнение с двадцатью сообщениями, 128 MB и 8 секунд на сообщение. Стоимость
складывается не только из времени выполнения Lambda, но также из SQS-запросов,
журналов, метрик и сигналов тревоги.

Для оценки мощности боевой системы учитывай:

```text
пиковую скорость поступления
среднюю и p95 продолжительность
размер пакета и полезной нагрузки
лимиты соединений или API нижестоящей системы
SLO по возрасту очереди
повторы и поведение DLQ
региональный бюджет одновременных вызовов Lambda
стоимость одного завершённого бизнес-действия
```

Схема оценки боевой системы:

```text
пиковая скорость поступления
  - определить требуемую скорость обработки
  - определить требуемое число одновременных вызовов
  - проверить нижестоящую систему, квоту и стоимость
  - проверить SLO по возрасту очереди
```

## 14. Проверка результата

Урок завершён, если:

- проходят 8 тестов Python;
- проходят 8 native-тестов Terraform;
- сопоставление находится в состоянии `Enabled`;
- его `MaximumConcurrency` равна `2`;
- зарезервированная мощность (`reserved concurrency`) функции по умолчанию отсутствует;
- всплеск из 20 сообщений принят без отклонённых записей;
- выборки показывают накопление, а затем опустошение очереди;
- журналы содержат несколько `request_id` и завершённые `task_id`;
- число одновременных вызовов (`concurrency`) Lambda не превышает лимит источника в изолированной лаборатории;
- метрика `Throttles` при нормальной ограниченной обработке остаётся нулевой;
- обе небезопасные конфигурации Terraform отклоняются;
- ты можешь объяснить, почему глубина и возраст требуют бизнес-цели.

## 16. Итоговая модель

Запомни:

1. Одновременное выполнение `concurrency` показывает текущую работу, а пропускная способность `throughput` - число завершённых заданий за единицу времени.
2. Очередь хранит нагрузку, когда скорость поступления выше скорости обработки.
3. `MaximumConcurrency` ограничивает один источник SQS и не резервирует мощность.
4. Зарезервированная мощность относится ко всей функции и занимает квоту аккаунта.
5. Резервирование мощности не прогревает среды выполнения.
6. Ограничение вызова означает отказ из-за нехватки мощности, а не нормальное управление потоком.
7. Глубина показывает объём, а возраст старейшего сообщения - давление на задержку.
8. Приблизительные атрибуты SQS нужно сопоставлять с метриками и журналами Lambda.
9. Повышать лимит безопасно только с учётом нижестоящей системы, квоты, стоимости и SLO.
10. Масштабирование не заменяет идемпотентность и частичный ответ по пакету.
