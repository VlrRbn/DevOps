# Урок 82. Lambda и SQS Event Source Mapping

## 1. Зачем нужен этот урок

В уроке 80 SQS была очередью назначения для итоговой ошибки. Сначала отправитель асинхронно вызывал Lambda, затем сама Lambda управляла внутренними повторами. Только после исчерпания повторов служба Lambda помещала в SQS служебную запись о неуспешном вызове.
В уроке 81 одну бизнес-операцию сделали идемпотентной.
Теперь SQS хранит исходные задания, которые должна обработать функция:

```text
отправитель
-> исходная очередь SQS
-> Lambda event source mapping опрашивает очередь
-> Lambda вызывает handler с пакетом сообщений
-> успешные сообщения подтверждаются
-> неудачные сообщения повторяются или перемещаются в DLQ
```

Это важное различие. Асинхронная отправка события в Lambda и опрос SQS службой
Lambda — разные механизмы доставки с разными правилами повторов.

| Механизм                 | Кто получает исходное событие | Где управляются повторы                            |
| ------------------------ | ----------------------------- | -------------------------------------------------- |
| Асинхронный вызов        | Сначала Lambda                | Во внутренней очереди Lambda                       |
| SQS event source mapping | Сначала SQS                   | Через видимость и повторную доставку сообщения SQS |

Главный вопрос урока:

> Как одному вызову Lambda обработать несколько сообщений SQS, но не повторять
> все успешные сообщения из-за ошибки только в одной записи?

Для этого используется частичный ответ по пакету (partial batch response):

```json
{
  "batchItemFailures": [
    {
      "itemIdentifier": "failed-02-sqs-message-id"
    }
  ]
}
```

```text
passed-01-sqs-message-id -> success
failed-02-sqs-message-id -> failure
passed-03-sqs-message-id -> success
-> batchItemFailures = [failed-02-sqs-message-id.messageId]
-> Lambda удаляет passed-01 и passed-03
-> failed-02 снова становится видимым
-> повторяется только failed-02
```

Таким образом, механизм решает проблему лишних повторов успешных соседних записей.

Он не исправляет причину ошибки `failed-02-sqs-message-id`. Он лишь изолирует эту запись от остального пакета.

SQS и Lambda event source mapping работают по модели доставки `как минимум один раз`
(at-least-once delivery): сообщение будет доставлено хотя бы один раз, но иногда может прийти повторно.

Сравнительная таблица:

| Свойство                  | Асинхронный вызов + место назначения | SQS event source mapping |
| ------------------------- | -------------------------------- | ------------------------ |
| Первоначальный получатель | Lambda                           | SQS                      |
| Что хранит очередь        | Итоговую запись об ошибке        | Исходное задание         |
| Кто управляет получением  | Внутренний механизм Lambda       | Механизм опроса Lambda   |
| Единица повтора           | Асинхронное событие              | Сообщение или пакет SQS  |

## 2. Результаты урока

После урока ты сможешь:

- отличить очередь итоговых ошибок Lambda от SQS event source mapping;
- объяснить, кто опрашивает SQS и кто удаляет успешные сообщения;
- проверить контракт пакетного события SQS;
- независимо обработать несколько записей внутри одного вызова;
- вернуть `batchItemFailures` с точными значениями SQS `messageId`;
- объяснить тайм-аут видимости (visibility timeout) и вычислить его безопасный минимум;
- настроить исходную очередь, DLQ и политики переноса сообщений;
- объяснить, почему ошибка одной записи может не увеличить метрику Lambda `Errors`;
- проследить путь проблемного сообщения (poison message) через повторы до DLQ;
- объяснить, почему частичный ответ не заменяет идемпотентность.

## 3. Ментальная модель

### 3.1. Очередь ошибок — не источник событий

Урок 80:

```text
AWS CLI вызывает Lambda асинхронно
-> Lambda управляет внутренней очередью повторов
-> итоговая запись об ошибке отправляется в SQS
```

SQS находилась в конце потока.

Сообщение в SQS означало примерно следующее:

```text
Lambda не смогла окончательно обработать асинхронное событие
-> создана итоговая запись об ошибке
-> запись отправлена в destination queue
```

Повторами до этого момента управляла Lambda, а не SQS.

Урок 82:

```text
отправитель передаёт сообщение в SQS
-> SendMessage
-> исходная очередь SQS
-> Lambda poller получает сообщение
-> event source mapping вызывает функцию
```

SQS находится в начале рабочего потока.

Граница терминов:

```text
destination queue
-> очередь получает данные от Lambda после обработки

source queue
-> Lambda получает данные из очереди для обработки
```

В уроке 80 SQS хранила итоговую запись об ошибке. В этом уроке SQS хранит исходное задание.

Назначение очереди:

| Вопрос                            | Место назначения из урока 80           | Источник из урока 82                      |
| --------------------------------- | -------------------------------------- | ----------------------------------------- |
| Что хранится                      | Итоговая запись об ошибке              | Исходное задание                          |
| Где находится очередь             | После Lambda                           | Перед Lambda                              |
| Кто инициирует обработку          | Отправитель вызывает Lambda            | Механизм опроса Lambda читает SQS         |
| Кто управляет основными повторами | Асинхронный вызов Lambda               | Видимость и повторная доставка SQS        |
| Может ли сообщение попасть в DLQ  | Место назначения уже является итогом Lambda | SQS переносит сообщение по политике переноса |

### 3.2. Lambda управляет опросом и подтверждением

Handler не вызывает `ReceiveMessage` и `DeleteMessage` самостоятельно.
Это делает event source mapping до и после вызова функции:

```text
Lambda poller
-> вызывает ReceiveMessage у исходной SQS
-> сообщение становится невидимым
-> формирует событие Records[]
-> event source mapping вызывает handler
-> handler возвращает результат
-> Lambda удаляет успешные сообщения через DeleteMessage
```

Для проблемной записи с частичным ответом по пакету:

```text
handler возвращает messageId в batchItemFailures
-> Lambda не удаляет эту запись
-> заканчивается visibility timeout
-> сообщение снова становится видимым
```

Роли выполнения всё равно нужны действия:

```text
sqs:ReceiveMessage - Получить сообщения из исходной очереди
sqs:DeleteMessage - Удалить успешно обработанные сообщения
sqs:GetQueueAttributes - Читать параметры очереди, необходимые механизму опроса
```

Они ограничены точным ARN исходной очереди. Роль выполнения не читает DLQ:
проверка и исправление таких сообщений относятся к обязанностям оператора.

Важно разделять две сущности:

```text
Lambda poller
-> фактически выполняет автоматический опрос

execution role
-> разрешает этому механизму работать с очередью
```

В отличие от интеграции с отправкой событий, например уведомления S3, для SQS event source mapping внутри
одного аккаунта не требуется `aws_lambda_permission` с субъектом `sqs.amazonaws.com`.
Lambda сама управляет механизмом опроса и обращается к SQS через роль выполнения функции.
Для очереди в другом аккаунте дополнительно понадобилась бы подходящая политика очереди SQS.

Кто удаляет сообщение?

```text
handler успешно завершил обработку записи
-> Lambda интерпретирует результат
-> Lambda удаляет сообщение из SQS
```

При включённом частичном ответе по пакету Lambda сопоставляет результат с конкретными `messageId`:

```text
messageId отсутствует в batchItemFailures
-> запись считается успешной
-> Lambda удаляет её

messageId присутствует в batchItemFailures
-> запись считается неуспешной
-> Lambda не удаляет её
```

Разделение ответственности:

| Компонент            | Ответственность                             |
| -------------------- | ------------------------------------------- |
| Отправитель          | Выполняет `SendMessage`                     |
| SQS                  | Хранит сообщение и управляет его видимостью |
| Механизм опроса Lambda | Получает сообщения                        |
| Event source mapping | Формирует пакет и запускает функцию         |
| Handler              | Обрабатывает записи и возвращает результат  |
| Lambda               | Удаляет успешные сообщения                  |
| Роль выполнения      | Разрешает доступ к исходной очереди         |

### 3.3. Один пакет — один вызов Lambda

Одно событие может содержать несколько записей:

```text
одно сообщение SQS
-> одна запись Records[]

несколько сообщений SQS
-> несколько записей Records[]
-> один вызов handler
event
└── Records
    ├── Records[0]
    ├── Records[1]
    └── Records[2]
```

Handler запускается один раз для всего массива `Records[]`, а затем код функции
самостоятельно проходит по отдельным записям.

`batch_size = 5` — пакет может содержать от 1 до 5 записей. Это верхняя граница, а не обещание.
Lambda может вызвать функцию с меньшим числом записей из-за глубины очереди, времени
накопления пакета или ограничения размера события.

Окно накопления тоже задаёт максимальное ожидание. Заполненный пакет может быть передан раньше.

| Параметр                         | Значение | Что означает                              |
| -------------------------------- | -------: | ----------------------------------------- |
| `BatchSize`                      |      `5` | Не более пяти записей в одном вызове      |
| `MaximumBatchingWindowInSeconds` |      `5` | Не более пяти секунд на накопление пакета |

Ты должен различать три уровня:

```text
SQS message
-> одно отдельное сообщение

Records[]
-> пакет полученных сообщений

Lambda invocation
-> один запуск handler для всего пакета
```

### 3.4. По умолчанию пакет обрабатывается целиком

Без частичного ответа по пакету Lambda оценивает результат всего вызова, а не каждой записи отдельно.

Без частичного ответа:

```text
message A -> success
message B -> failure
message C -> success
handler выбрасывает исключение
-> весь пакет считается неуспешным
-> Lambda не удаляет A, B и C
-> заканчивается visibility timeout
-> A, B и C снова становятся видимыми
-> весь пакет может быть доставлен повторно
```

Поэтому полный отказ пакета создаёт две проблемы:

| Проблема               | Причина                                |
| ---------------------- | -------------------------------------- |
| Лишние вызовы Lambda   | Успешные записи снова попадают в пакет |
| Повтор бизнес-действий | Успех записи не означает exactly-once  |

Без частичного ответа по пакету возможны только два результата:

```text
handler завершился успешно
-> весь пакет считается успешным

handler выбросил исключение
-> весь пакет считается неуспешным
```

### 3.5. Частичный ответ по пакету

Частичный ответ по пакету позволяет handler сообщить Lambda:

- какие записи завершились ошибкой.

Event source mapping включает:

```hcl
function_response_types = ["ReportBatchItemFailures"]
```

Эта настройка сообщает Lambda, что ответ handler нужно интерпретировать как частичный результат обработки пакета.

Handler должен вернуть объект такого формата:

```json
{
  "batchItemFailures": [
    {
      "itemIdentifier": "точный-sqs-messageId"
    }
  ]
}
```

`itemIdentifier` — это точный SQS `messageId` неудачной записи.

Handler перехватывает ошибки отдельных записей и возвращает только их идентификаторы:

```text
message A -> success
message B -> failure
message C -> success

handler:
-> перехватывает ошибку B
-> добавляет B.messageId в batchItemFailures
-> продолжает обработку C
-> возвращает нормальный ответ

Результат:

A отсутствует в batchItemFailures
-> Lambda удаляет A

B присутствует в batchItemFailures
-> Lambda не удаляет B
-> B повторяется после visibility timeout

C отсутствует в batchItemFailures
-> Lambda удаляет C
```

Контракт должен выполняться с обеих сторон:

| Сторона | Требование |
|---|---|
| Terraform | Включить `ReportBatchItemFailures` |
| Handler | Вернуть корректный JSON `batchItemFailures` |
| Неудачная запись | Использовать точный SQS `messageId` |
| Полностью успешный пакет | Вернуть пустой список |

Если handler выбросит исключение за пределы обработки отдельной записи, Lambda
посчитает неудачным весь пакет.

Граница идентификаторов:

```text
messageId
-> идентификатор записи для Lambda и SQS batch response

task_id
-> бизнес-ключ, возможный idempotency key

messageId != task_id
```

### 3.6. Тайм-аут видимости — это аренда

Когда механизм опроса Lambda выполняет `ReceiveMessage`, SQS временно скрывает сообщение от других потребителей:

```text
сообщение видимо
-> Lambda получает его
-> сообщение становится невидимым
-> handler обрабатывает пакет
```

Этот период называется тайм-аутом видимости.

Успешная обработка:

```text
Lambda получает сообщение
-> сообщение становится невидимым
-> handler успешно обрабатывает запись
-> Lambda выполняет DeleteMessage
-> сообщение окончательно удалено
```

При успехе Lambda удаляет сообщение. При ошибке оно снова становится видимым
после окончания тайм-аута видимости.

Ошибка обработки:

```text
Lambda получает сообщение
-> сообщение становится невидимым
-> запись завершилась ошибкой
-> Lambda не удаляет сообщение
-> visibility timeout заканчивается
-> сообщение снова становится видимым
-> возможна повторная доставка
```

AWS рекомендует:

```text
visibility timeout
>= 6 × Lambda function timeout + maximum batching window
```

Значения лаборатории:

```text
6 × 10 секунд + 5 секунд = 65 секунд
настроенный visibility timeout = 70 секунд
```

Запас учитывает ограничение пропускной способности (throttling) и повторы вокруг обработки пакета. Если тайм-аут видимости короче
реального времени обработки, одно сообщение может одновременно попасть в несколько воркеров.

### 3.7. Политика переноса (redrive) и DLQ

У исходной очереди настроено:

```text
maxReceiveCount = 3
DLQ = lab82-...-sqs-dlq
```

После исчерпания числа получений SQS перемещает проблемное сообщение в DLQ. В лаборатории
выбрано три получения.

У DLQ также есть политика, разрешающая перенос только из указанной очереди:

```text
redrivePermission = byQueue
sourceQueueArns = [точный ARN исходной очереди]
```

Так посторонняя очередь не сможет выбрать DLQ этой лаборатории.

Проблемное сообщение (poison message) стабильно вызывает ошибку при каждой попытке.

В лаборатории это сообщение с:

```text
{
  "task_id": "report-poison-001",
  "action": "generate_report",
  "should_fail": true
}
```

`generate_report` намеренно выбрасывает `RuntimeError`, поэтому запись каждый раз
попадает в `batchItemFailures`.

Схема:

```text
SQS delivery
-> Lambda обрабатывает запись
-> generate_report выбрасывает RuntimeError
-> handler перехватывает исключение
-> messageId добавляется в batchItemFailures
-> Lambda не удаляет сообщение
-> visibility timeout истекает
-> сообщение доставляется повторно
-> ApproximateReceiveCount увеличивается
-> maxReceiveCount исчерпан
-> SQS перемещает сообщение в DLQ
```

- handler сообщает об ошибке записи
- Lambda не удаляет запись
- SQS считает получения и выполняет перенос

Политика переноса (`redrive_policy`) отвечает на два вопроса:

- куда переносить сообщение
- после скольких получений переносить

Логически:

```json
{
  "deadLetterTargetArn": "<ARN DLQ>",
  "maxReceiveCount": 3
}
```

`redrive_allow_policy` — другая политика. Она находится на DLQ и определяет, каким
исходным очередям разрешено использовать эту DLQ.

| Политика               | Где находится    | Что контролирует                         | Основные поля |
| ---------------------- | ---------------- | ---------------------------------------- | -------------- |
| `redrive_policy`       | Исходная очередь | Целевую DLQ и `maxReceiveCount`          | deadLetterTargetArn, maxReceiveCount |
| `redrive_allow_policy` | DLQ              | Какие очереди могут использовать эту DLQ | redrivePermission, sourceQueueArns |

### 3.8. Частичный ответ не даёт Exactly-Once

SQS event source mapping работает по модели:

```text
at-least-once
-> сообщение будет доставлено как минимум один раз
-> иногда одно сообщение может быть доставлено повторно
```

Схема:

```text
Lambda получила сообщение
-> handler создал отчёт
-> отчёт успешно отправлен клиенту
-> до подтверждения сообщения произошёл сбой
-> Lambda не удалила сообщение из SQS
-> visibility timeout закончился
-> сообщение доставлено повторно
-> handler снова пытается создать и отправить отчёт
```

Частичный ответ по пакету не знает, произошло ли внутри обработки необратимое действие до ошибки.

```text
partial batch response
-> изолирует ошибку одной записи
-> уменьшает повторы успешных соседей

partial batch response
!= exactly-once
!= гарантия однократного бизнес-действия
```

Для платежей, писем и выдачи ресурсов этот урок нужно объединить с автоматом идемпотентности из урока 81.

В сообщении лаборатории есть стабильный бизнес-идентификатор:

```json
{
  "task_id": "report-success-001",
  "action": "generate_report"
}
```

Именно `task_id`, а не SQS `messageId`, можно использовать как ключ идемпотентности.

```text
первая доставка:
task_id = report-success-001
-> создать claim
-> выполнить действие
-> сохранить результат

повторная доставка:
task_id = report-success-001
-> найден завершённый результат
-> не выполнять действие повторно
-> вернуть сохранённый результат
```

| Идентификатор   | Назначение                                          |
| --------------- | --------------------------------------------------- |
| SQS `messageId` | Указать Lambda, какую транспортную запись повторить |
| `task_id`       | Не допустить повторного бизнес-действия             |

```text
batchItemFailures
-> использует messageId

идемпотентность
-> использует стабильный task_id
```

| Механизм               | Какую проблему решает                          | Чего не гарантирует           |
| ---------------------- | ---------------------------------------------- | ----------------------------- |
| Тайм-аут видимости     | Временно скрывает сообщение во время обработки | Успешную обработку            |
| Частичный ответ по пакету | Изолирует неудачную запись внутри пакета    | Exactly-once                  |
| DLQ                    | Ограничивает бесконечные повторы               | Исправление причины ошибки    |
| Идемпотентность        | Предотвращает повтор бизнес-действия           | Отсутствие повторной доставки |

## 4. Архитектура лаборатории

```text
                        исходное задание
                              |
                              v
+------------+      +-----------------------+
| отправитель| ---> | исходная очередь SQS  |
+------------+      | visibility = 70s      |
                    | maxReceiveCount = 3   |
                    +-----------+-----------+
                                |
                                | Lambda poller
                                v
                    +-----------------------+
                    | event source mapping  |
                    | batch size = 5        |
                    | batch window = 5s     |
                    | partial response = on |
                    +-----------+-----------+
                                |
                                v
                    +-----------------------+
                    | Lambda consumer       |
                    | обработка Records[]   |
                    +-----------+-----------+
                                |
                  неудачные записи повторяются
                                |
                       повторы исчерпаны
                                v
                    +-----------------------+
                    | SQS DLQ               |
                    | retention = 14 дней   |
                    +-----------------------+
```

### 1. Исходная очередь SQS

Она принимает задания от отправителя.

Назначение:

```text
хранить исходные сообщения
-> временно скрывать полученные сообщения
-> повторно показывать неподтверждённые сообщения
-> передавать исчерпавшие повторы сообщения в DLQ
```

### 2. Event source mapping

Это связующее звено между исходной очередью и Lambda.

Он отвечает за:

```text
опрос исходной очереди
-> формирование Records[]
-> вызов Lambda
-> интерпретацию batchItemFailures
-> удаление успешных сообщений
```

Это управляемая конфигурация Lambda.

### 3. Потребитель событий Lambda

Функция получает пакет записей и проверяет каждую независимо:

```text
Records[]
-> проверить оболочку SQS
-> разобрать body
-> проверить бизнес-поля
-> выполнить generate_report
```

Для каждой записи возможен результат:

```text
успех
-> запись не добавляется в batchItemFailures

ошибка записи
-> точный messageId добавляется в batchItemFailures
```

Если нарушен контракт всего события, например отсутствует `messageId`, handler завершает ошибкой весь вызов.

### 4. DLQ

DLQ хранит сообщения, которые исчерпали бюджет получений.

Путь сообщения:

```text
ошибка обработки
-> сообщение не удалено
-> visibility timeout закончился
-> повторная доставка
-> три получения исчерпаны
-> SQS перемещает сообщение в DLQ
```

DLQ не участвует в обычной обработке успешных сообщений.

Два разных пути после Lambda:

```text
успех
-> DeleteMessage
-> сообщение удалено

ошибка записи
-> messageId в batchItemFailures
-> сообщение повторяется
-> затем возможен перенос в DLQ
```

Наблюдаемость:

| Сигнал                                     | Что показывает                                |
| ------------------------------------------ | --------------------------------------------- |
| Lambda `Errors`                            | Весь вызов Lambda завершился ошибкой          |
| `ApproximateAgeOfOldestMessage`            | Исходная очередь обрабатывается с отставанием |
| `ApproximateNumberOfMessagesVisible` в DLQ | Есть сообщения, исчерпавшие бюджет повторов   |

Параметры с их назначением:

| Параметр                  | Где настроен                    | Зачем                               |
| ------------------------- | ------------------------------- | ----------------------------------- |
| `70s`                     | Исходная очередь                | Безопасный тайм-аут видимости       |
| `3`                       | Политика переноса исходной очереди | Ограничить число получений       |
| `5` сообщений             | Event source mapping            | Верхняя граница пакета              |
| `5s`                      | Event source mapping            | Максимальное окно накопления        |
| `ReportBatchItemFailures` | Event source mapping            | Включить частичный результат        |
| `14 дней`                 | DLQ                             | Срок хранения проблемного сообщения |

## 5. Разбор реализации

### 5.1. Проверка записи

Открой функцию проверки:

```bash
sed -n '14,52p' ../app/lambda_function.py
```

`parse_record` проверяет два контракта:

1. Оболочка SQS:
   - запись является объектом;
   - `messageId` — непустая строка;
   - поле `body` — строка.
2. Тело бизнес-сообщения:
   - поле `body` содержит корректный JSON-объект;
   - `task_id` не пуст;
   - `action` равен `generate_report`;
   - `should_fail` имеет логический тип `boolean`.

Схема:

```text
SQS record
-> record является объектом?
-> есть непустой messageId?
-> body является строкой?
-> body разбирается как JSON-объект?
-> есть task_id?
-> action = generate_report?
-> should_fail является boolean?
-> запись разрешена к обработке
```

Отсутствие `messageId` — особый случай. Handler не может указать неизвестную запись в `batchItemFailures`, поэтому безопаснее завершить ошибкой весь вызов, чем подтвердить работу, которую невозможно точно идентифицировать.

### 5.2. Изоляция отдельных записей

Открой цикл обработки пакета:

```bash
sed -n '68,118p' ../app/lambda_function.py
```

Главная задача `process_batch()`:

```text
получить Records[]
-> обработать каждую запись отдельно
-> собрать messageId только неудачных записей
-> вернуть batchItemFailures
```

Сначала функция проверяет общий контракт события:

```text
event должен быть объектом
-> event.Records должен быть списком
```

Если общий контракт нарушен, обработать отдельные записи невозможно, поэтому `process_batch()` выбрасывает исключение и весь вызов Lambda завершается ошибкой.

#### Проверка `messageId`

Для каждой записи `messageId` проверяется **до** входа в `try/except` отдельной записи:

```text
получить запись из Records[]
-> проверить, что запись является объектом
-> получить messageId
-> проверить, что messageId — непустая строка
-> только после этого начать изолированную обработку записи
```

Это необходимо потому, что частичный ответ по пакету может обозначить неудачную запись только точным SQS `messageId`.

Если `messageId` отсутствует:

```text
нет messageId
-> нельзя сформировать itemIdentifier
-> нельзя точно обозначить неудачную запись
-> MessageContractError не перехватывается на уровне записи
-> исключение выходит из process_batch
-> весь вызов Lambda завершается ошибкой
```

То есть запись без `messageId` не изолируется.

#### Граница изоляции записи

После успешной проверки `messageId` начинается `try/except` конкретной записи:

```python
try:
    _, message = parse_record(record)
    result = processor(message)
```

Внутри этой границы выполняются две операции:

```text
parse_record
-> проверяет body и бизнес-контракт сообщения

processor
-> выполняет бизнес-обработку
-> по умолчанию это generate_report
```

#### Успешная запись

Если `parse_record()` и `processor()` завершились успешно:

```text
записать sqs_message_processed в журнал
-> не добавлять messageId в failures
-> перейти к следующей записи
```

Запись в журнал содержит:

```text
event = sqs_message_processed
message_id
task_id
report_id
```

#### Неудачная запись

Если `parse_record()` или `processor()` выбросили исключение, оно попадает в:

```python
except Exception as error:
```

После этого функция:

```text
записывает sqs_message_failed в журнал
-> указывает message_id
-> указывает тип и текст ошибки
-> добавляет точный messageId в failures
-> продолжает цикл
```

Формируемая запись ошибки:

```python
failures.append({
    "itemIdentifier": message_id
})
```

Ключевой момент:

```text
исключение возникло внутри parse_record или processor
-> поднялось обратно в process_batch
-> except внутри process_batch его перехватил
-> исключение не дошло до lambda_handler
-> цикл продолжается
-> следующая запись тоже обрабатывается
```

Именно это называется изоляцией ошибки одной записи.

#### Ответ `process_batch()`

После обработки всех записей функция возвращает:

```python
return {
    "batchItemFailures": failures
}
```

При нормальном завершении возможны два основных ответа.

Все записи успешны:

```json
{
  "batchItemFailures": []
}
```

Есть неудачные записи:

```json
{
  "batchItemFailures": [
    {
      "itemIdentifier": "message-bad"
    }
  ]
}
```

Но если исключение возникло вне `try/except` отдельной записи, например из-за отсутствующего `messageId`, `process_batch()` не возвращает `batchItemFailures`: весь вызов завершается ошибкой.

#### Пример: пакет A, B, C

```text
A -> корректная запись
B -> should_fail = true
C -> корректная запись
```

Обработка записи A:

```text
parse_record успешно
-> processor успешно
-> записан sqs_message_processed
-> A.messageId не добавляется в failures
```

Обработка записи B:

```text
parse_record успешно
-> processor вызывает generate_report
-> generate_report выбрасывает RuntimeError
-> except внутри process_batch перехватывает RuntimeError
-> записан sqs_message_failed
-> B.messageId добавляется в failures
```

Обработка записи C:

```text
цикл не был остановлен ошибкой B
-> parse_record успешно
-> processor успешно
-> записан sqs_message_processed
-> C.messageId не добавляется в failures
```

Итоговый ответ:

```json
{
  "batchItemFailures": [
    {
      "itemIdentifier": "B.messageId"
    }
  ]
}
```

При включённом `ReportBatchItemFailures` результат интерпретируется так:

```text
A отсутствует в batchItemFailures
-> Lambda удаляет A

B присутствует в batchItemFailures
-> Lambda не удаляет B
-> после visibility timeout B может быть доставлена повторно

C отсутствует в batchItemFailures
-> Lambda удаляет C
```

Итоговая граница:

```text
ошибка внутри try отдельной записи
-> исключение перехвачено
-> только messageId этой записи добавлен в batchItemFailures
-> обработка пакета продолжается
```

```text
ошибка до try отдельной записи
-> исключение не перехвачено на уровне записи
-> process_batch завершается ошибкой
-> весь вызов Lambda считается неуспешным
```

### 5.3. Контракт Terraform

Проверь очередь и event source mapping:

- `queues.tf`;
- `event_source_mapping.tf`;
- `function_execution_role.tf`.

Важные связи:

```text
исходная очередь
-> redrive policy указывает на DLQ ARN

DLQ
-> разрешает использование только исходной очереди ARN

event source mapping
-> читает исходную очередь ARN
-> вызывает нужную Lambda ARN
-> включает ReportBatchItemFailures

execution role
-> имеет доступ только к исходной очереди ARN
```

Очереди SQS:

1. Что проверяем: исходную очередь, DLQ и политики переноса.
2. Что ожидаем:
  - исходная очередь имеет тайм-аут видимости;
  - её `redrive_policy` указывает на ARN DLQ;
  - установлен `maxReceiveCount`;
  - DLQ имеет `redrive_allow_policy`, разрешающую только исходную очередь.
3. Что доказывает результат: Terraform связывает исходную очередь и DLQ в правильном направлении.
4. Чего не доказывает: что сообщение уже повторялось или действительно оказалось в DLQ.
5. Уровень: Terraform и SQS.

Event source mapping:

1. Что проверяем: связь исходной очереди с Lambda и настройки пакетной обработки.
2. Что ожидаем:
  - `event_source_arn` указывает на исходную очередь;
  - `function_name` указывает на Lambda;
  - настроены размер пакета и окно накопления;
  - включён `ReportBatchItemFailures`.
3. Что доказывает результат: Terraform описывает нужный контракт event source mapping.
4. Чего не доказывает: что сопоставление уже создано в AWS и находится в состоянии `Enabled`.
5. Уровень: Terraform и event source mapping.

Пояснение к `depends_on`:

```text
depends_on
-> обеспечивает порядок создания IAM policy и mapping
!= выдаёт IAM-разрешения
```

Роль выполнения:

1. Что проверяем: права Lambda во время выполнения.
2. Что ожидаем:
  - права CloudWatch Logs ограничены группой журналов функции;
  - разрешены `sqs:ReceiveMessage`, `sqs:DeleteMessage`, `sqs:GetQueueAttributes`;
  - SQS `Resource` — точный ARN исходной очереди;
  - нет доступа к DLQ;
  - нет шаблона `Resource = "*"`.
3. Что доказывает результат: механизм опроса Lambda получает минимальные необходимые полномочия
через роль выполнения.
4. Чего не доказывает: что роль реально используется созданной функцией или что API-вызовы
SQS уже успешно выполнялись.
5. Уровень: Terraform и IAM.

## 8. Проверка Event Source Mapping

Что сейчас проверяем:

1. Что проверяем:
    - созданный в AWS event source mapping.
2. Какой результат ожидаем:

4. Чего это не доказывает:
    - что конкретное сообщение уже было получено, обработано или удалено.
5. Уровень проверки:
    - event source mapping и AWS Lambda.

```bash

  --uuid "$MAPPING_UUID" \
  --region "$AWS_REGION" \
  --query '{State:State,LastResult:LastProcessingResult,BatchSize:BatchSize,BatchWindow:MaximumBatchingWindowInSeconds,ResponseTypes:FunctionResponseTypes,Source:EventSourceArn}' \
```

## 11. Частичная ошибка и ошибка всего вызова

Ветка проблемного сообщения возвращает нормальный ответ handler с одной неудачной
записью. Метрика Lambda `Errors` может остаться равной нулю.

Проверяем, что запись не содержит корректного `messageId`:

```text
нет messageId
-> нельзя сформировать itemIdentifier
-> исключение возникает до try/except записи
-> process_batch не возвращает batchItemFailures
-> весь вызов Lambda завершается ошибкой
```

Схема:

```text
invalid-batch-event.json
-> прямой Lambda Invoke
-> lambda_handler
-> process_batch
-> запись не содержит messageId
-> MessageContractError выходит из process_batch
-> FunctionError = Unhandled
```

Что сейчас проверяем:

1. Что проверяем:
    - завершится ли весь вызов Lambda необработанной ошибкой, если запись невозможно обозначить точным `messageId`.
2. Какой результат ожидаем:
    - метаданные содержат `StatusCode = 200` и `FunctionError = Unhandled`; полезная нагрузка содержит `errorMessage` с упоминанием `messageId`.
3. Что это доказывает:
    - Lambda Invoke API успешно вызвал функцию, но handler завершился необработанным исключением.
4. Чего это не доказывает:
    - работу SQS, повторную доставку, изменение DLQ или удаление сообщений.
5. Уровень проверки:
    - AWS Lambda.

Теперь напрямую вызови Lambda с намеренно некорректной оболочкой SQS. Команда
обходит опрос очереди и проверяет границу ошибки всего вызова:

```bash
aws lambda invoke \
  --function-name "$FUNCTION_NAME" \
  --region "$AWS_REGION" \
  --cli-binary-format raw-in-base64-out \
  --payload fileb://events/invalid-batch-event.json \
  evidence/invalid-batch-response.json \
  > evidence/invalid-batch-metadata.json

jq . evidence/invalid-batch-metadata.json
jq . evidence/invalid-batch-response.json
```

Ожидается:

```text
StatusCode = 200
-> Lambda Invoke API принял и выполнил запрос к функции

FunctionError = Unhandled
-> handler не вернул нормальный результат
-> исключение вышло из lambda_handler
-> весь вызов завершился ошибкой

запись не содержит корректный messageId
-> process_batch выбрасывает MessageContractError
-> исключение не перехватывается на уровне записи
-> batchItemFailures не возвращается
-> весь вызов завершается ошибкой
```

Прямой вызов ничего не подтверждает и не удаляет в SQS.
Он используется только для демонстрации границы контракта.

Поэтому нельзя сразу возвращать его в исходную очередь.

Правильный порядок:

1. Проверить тело сообщения и CloudWatch Logs.
2. Определить причину: код, данные, IAM или внешняя зависимость.
3. Исправить причину.
4. Развернуть новую версию.
5. Проверить исправление контролируемым сообщением.
6. Согласовать возврат сообщений.
7. Возвращать сообщения с ограниченной скоростью.
8. Следить за возрастом сообщений в исходной очереди, Lambda `Errors` и глубиной DLQ.

Лаборатория не автоматизирует возврат из DLQ: повтор неизменённого проблемного сообщения
создаст цикл ошибок.

### Упражнение 4. Свяжи результат с уроком 81

Представь, что `generate_report` отправляет платное письмо, а затем процесс теряет ответ.

Возможная ситуация:

```text
Lambda отправила письмо
-> внешний сервис выполнил операцию
-> Lambda потеряла ответ или завершилась до подтверждения SQS
-> сообщение доставлено повторно
-> Lambda отправляет письмо второй раз
```

Частичный ответ по пакету решает только вопрос повторной доставки:

```text
какой messageId обработан успешно
какой messageId нужно повторить
```

Но он не знает, успел ли внешний сервис выполнить действие до ошибки.

Поэтому:

```text
доставка SQS «как минимум один раз» (at-least-once)
+
неатомарный внешний побочный эффект (side effect)
=
риск повторного бизнес-действия
```

### Решение

В качестве ключа идемпотентности используй:

```text
task_id = report-poison-001
```

Схема:

```text
получить сообщение
-> проверить task_id в хранилище идемпотентности
-> если task_id новый — зарезервировать и выполнить действие
-> сохранить результат
-> если task_id уже завершён — вернуть сохранённый результат
-> не выполнять побочный эффект повторно
```

5. Уровень:
  - AWS Lambda event source mapping.

Проверь причину состояния:

```bash
aws lambda get-event-source-mapping \
  --uuid "$MAPPING_UUID" \
  --region "$AWS_REGION" \
  --query '{State:State,Reason:StateTransitionReason,LastResult:LastProcessingResult}' \
  --output json
```

Четыре основные причины:

1. Роли выполнения не хватает:
   `sqs:ReceiveMessage`
   `sqs:DeleteMessage`
   `sqs:GetQueueAttributes`
2. Lambda и SQS находятся в разных регионах
3. Тайм-аут Lambda больше тайм-аута видимости очереди
4. В сопоставлении указан неверный ARN исходной очереди

### Успешные сообщения повторяются вместе с проблемным сообщением

Это означает, что частичный ответ по пакету фактически не работает как задумано.

Проверь обе части частичного отчёта об ошибках:

```text
Event Source Mapping:
   FunctionResponseTypes = ["ReportBatchItemFailures"]

Handler:
   возвращает batchItemFailures с точным SQS messageId

После формирования partial response:
   handler НЕ выбрасывает исключение
```

Выброшенное исключение делает неудачным весь пакет.

### DLQ остаётся пустой

Если проблемное сообщение не появляется в DLQ, сначала нужно понять, **где оно сейчас находится в жизненном цикле**.

Проверь:

```bash
./scripts/inspect-queue.sh \
  "$SOURCE_QUEUE_URL" \
  "$AWS_REGION" \
  evidence/source-diagnostic.json

aws logs tail "$LOG_GROUP" \
  --region "$AWS_REGION" \
  --since 30m \
  --format short
```

Возможные причины:

```text
Сообщение сейчас невидимо:
   -> Lambda уже получила его
   -> visibility timeout ещё не истёк

maxReceiveCount ещё не исчерпан:
   -> сообщение всё ещё проходит повторные доставки

Event Source Mapping отключён:
   -> Lambda вообще не получает сообщения

Сообщение неожиданно обработалось успешно:
   -> Lambda подтвердила успех
   -> SQS удалила его
   -> в DLQ оно не попадёт

ApproximateNumberOfMessages ещё не обновился:
   -> SQS metrics/attributes имеют задержку
```

Как различить состояния:

```text
ApproximateNumberOfMessages > 0
-> сообщение видно в source queue

ApproximateNumberOfMessagesNotVisible > 0
-> сообщение сейчас у consumer / Lambda

оба = 0
+
есть sqs_message_processed
-> сообщение успешно удалено

оба = 0
+
есть повторяющиеся sqs_message_failed
+
DLQ > 0
-> сообщение уже ушло в DLQ
```

### Lambda `Errors` остаётся `0` для проблемного сообщения

В лаборатории это ожидаемо:

```text
generate_report -> RuntimeError
-> process_batch перехватил исключение
-> messageId добавлен в batchItemFailures
-> handler вернул корректный ответ
-> весь Lambda invocation завершился нормально
```

Чем тогда ловить такие ошибки:

```text
CloudWatch Logs
-> sqs_message_failed + message_id

DLQ depth
-> сообщение исчерпало retry budget

Source queue age
-> очередь начинает отставать
```

### Исходная очередь выглядит пустой во время обработки

Сообщение может быть невидимым, а не удалённым. Проверяй оба атрибута:

```text
ApproximateNumberOfMessages
-> видимые сообщения, готовые к получению

ApproximateNumberOfMessagesNotVisible
-> сообщения уже получены consumer'ом и скрыты visibility timeout
```

Не используй `receive-message` для проверки исходной очереди, пока Lambda её опрашивает.
Такое получение конкурирует с event source mapping и меняет видимость сообщения.

### Успешная запись всё равно выполнилась дважды

Это допустимо при доставке «как минимум один раз». Частичный ответ уменьшает один источник
дублей, но не устраняет их полностью. Защити реальное бизнес-действие границей
идемпотентности из урока 81.

```text
SQS повторно доставила task_id=123
-> Lambda проверяет idempotency key
-> видит, что task_id=123 уже выполнен
-> не повторяет бизнес-действие
```

## 15. Стоимость и эксплуатационные границы

Лаборатория использует:

- 1 × исходная очередь SQS
- 1 × DLQ
- 1 × Lambda
- 1 × event source mapping
- 1 × группа журналов CloudWatch
- 3 × сигнала тревоги CloudWatch

Основные источники стоимости:

- SQS
  -> `SendMessage`
  -> опрос
  -> повторные попытки
  -> диагностические запросы

- Lambda
  -> количество вызовов
  -> длительность обработки пакета

- CloudWatch Logs
  -> запись логов
  -> хранение логов

- сигналы тревоги CloudWatch
  -> три настроенных сигнала

## 18. Итоговая модель

Запомни:

1. SQS event source mapping — управляемый механизм опроса, а не место назначения Lambda.
2. Один вызов Lambda может содержать несколько записей SQS.
3. Без частичного ответа по пакету одна ошибка может повторить весь пакет.
4. `ReportBatchItemFailures` нужно включить в Terraform и реализовать в коде.
5. Тайм-аут видимости скрывает сообщение, но не подтверждает его.
6. Политика переноса в DLQ ограничивает повторную обработку проблемного сообщения.
7. Сообщение в DLQ нужно расследовать до повторной обработки.
8. Ошибка отдельной записи может не увеличить Lambda `Errors`.
9. Модель `как минимум один раз` (at-least-once) всё равно требует идемпотентных бизнес-действий.
